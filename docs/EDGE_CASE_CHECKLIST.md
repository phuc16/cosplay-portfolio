# Edge Case Checklist — Merch Shop / Order System

This is a coverage record, not a to-do list. It was generated on 2026-09-04 by
reading the full commit history of the `feature/order` branch (~320 commits,
diverged from `main`) plus the uncommitted working-tree changes present at
generation time. Every item below traces to an actual commit or diff — it
lists edge cases that have already been identified and fixed/guarded against,
not open work. See `docs/DECISIONS.md` for the "why" behind product/business
calls; this file focuses on the mechanical edge case and its guard.

## Checkout / Order Creation

- [x] Stock-reservation used a bare `FOR UPDATE` on a query joining `products`, which in MySQL locks every table read — including parent product rows acquired in variant-id order with no consistent relation to product ids, enabling cross-order deadlocks even though variant locks alone were correctly ordered — changed to `FOR UPDATE OF v` so only `product_variants` rows are locked.
- [x] `request_key` (idempotency key) is unique across *all* buyers, but replay lookup matched on the key alone, so a second submitter reusing/guessing someone else's key received that stranger's order (including `order_token`, exposing name/phone/email/address) — lookup now also requires the stored order's buyer email to match; cross-buyer collisions fail with `RequestKeyConflictError` instead of leaking data.
- [x] The buyer-email match added to fix the request_key leak itself broke on blank emails: two different buyers who both omitted email and reused the same request_key normalized to the same empty string and were treated as the same buyer, reopening the exact cross-buyer leak — a blank email on either side now never counts as a match.
- [x] Checkout memoized its idempotency key for the page's lifetime, so if the server ever returned a genuine `request_key_conflict` (e.g. a UUID collision), every retry resent the same colliding key and the buyer was stuck until a page reload — key is now regenerated specifically on that error before retrying.
- [x] `generateRequestKey`'s "no `crypto.randomUUID`" fallback branch called itself instead of a real fallback, so in every normal environment it recursed until stack overflow inside a `useState` initializer, blanking the entire checkout page — fixed to call the actual fallback and extracted into its own tested module.
- [x] An admin-set `shipping_fee` of exactly `0` was coerced to `null` by a `Number(x) || null` pattern (`0 || null` is `null` in JS) — switched to `Number.isFinite()` so a legitimate zero shipping fee persists as `0`.
- [x] `GET /api/orders/:token` echoed the raw DB row, exposing internal fields (`request_key`, `stock_released_at`) the buyer had no use for — response projected down to only the fields the order page renders.
- [x] Checkout accepted a fulfillment method (`pickup`/`ship`) the product's collection doesn't actually offer, producing e.g. a pickup order with no address on a ship-only collection — the requested method is now cross-checked against the collection's offered methods and rejected if unsupported.
- [x] A cart line referencing a deleted `variant_id` reused `OutOfStockError` with the literal string "không tồn tại" as if it were the item's name, showing a nonsense product name to the buyer — added a distinct `VariantNotFoundError` with its own message/code.
- [x] Stale `variant_id` in a buyer's localStorage cart caused an infinite "refresh and try again" loop since nothing let them identify/remove the bad line — `VariantNotFoundError` now carries the missing `variant_ids`; Checkout auto-removes exactly those lines from cart state and retries.
- [x] Order rate-limit and payment-proof-upload messages gave no count or wait time ("try again later") — now state the numeric cap and a concrete wait computed from `req.rateLimit.resetTime`.
- [x] *(uncommitted)* A cart line's collection stopped being "active" between add-to-cart and checkout (the seller closed the drop) — order creation now checks `collection.status` under the same row lock as the stock check and reports a distinct `collection_not_active` (409, quoting product+variant), the same client-recoverable shape as `out_of_stock`.
- [x] *(uncommitted)* `OutOfStockError`'s buyer-facing message quoted only the variant label ("Rất tiếc, "L" vừa hết hàng") with no product name, ambiguous when many products share a variant label like "L" or "A1" — message and error object now also carry/quote `productName`.
- [x] A second payment-proof upload for the same order could have co-existed with or been silently ignored next to the first — the upload now replaces the stored proof outright, verified by a test asserting the old URL is gone.
- [x] Payment-proof upload shared its rate-limit budget with order creation, so a buyer retrying a failed proof upload could burn through the same cap that gates placing new orders — given its own dedicated `proofLimiter` budget.
- [x] `createOrder` validated a collection's `end_at` (closed) but never checked `start_at`, so a buyer with a stale cart/variant_id in hand could check out before a scheduled drop's start even though the collection was correctly hidden from listings — `start_at` is now enforced alongside `end_at`.
- [x] Collection start/end scheduling sent the admin's `datetime-local` input to the server as a naive string, parsed server-side via `new Date(value)` in the server's own (UTC) timezone rather than the admin's actual (Vietnam, UTC+7) timezone — a 7-hour scheduling error. Fixed by converting to `.toISOString()` client-side before sending (the browser correctly resolves naive input as local time), and switching the public collection queries from `NOW()` to `UTC_TIMESTAMP()` to remove an implicit MySQL-session-timezone coupling.
- [x] Cart/Checkout only discovered a sold-out, closed, not-yet-started, or ended collection at order-submission time — after the buyer filled out the whole form. Cart and Checkout now validate against live collection/variant state up front and auto-remove the offending line(s), using structured `variant_id` data now carried on `VariantNotFoundError`/`OutOfStockError`/`CollectionNotActiveError`.
- [x] Deleting a product or collection with a live (pending/confirmed/shipped) order still referencing one of its variants would silently orphan `order_items` — `deleteProduct`/`deleteCollection` now run inside a transaction, row-lock (`FOR UPDATE`, ascending id) the affected variants, and throw `VariantInUseError` (409 `variant_in_use`) if any is still live-referenced, mirroring `replaceVariants`'s existing guard.

## Digital Products

- [x] The public collection API returned `delivery_link` for digital variants unconditionally, exposing a paid-content download link to any visitor before purchase or payment — `getPublicCollectionBySlug` now strips `delivery_link` on the public read path only (the admin path still needs it to manage the product).
- [x] COD checkout with a digital item in the cart made no sense (nothing to hand over on delivery) — COD is now rejected outright when the cart contains a digital item, `fulfillment_method` is auto-set to `digital`, and `delivery_link` is snapshotted onto `order_items` at order-creation time so a later catalog edit can't change what a paid buyer already received.
- [x] A confirmed digital order's delivery link needed to appear in its confirmation email, but only once actually paid, and never for a pending/cancelled order — gated on `status`, verified with dedicated template tests for pending/confirmed/cancelled and for mixed ship+digital orders.

## Order Lifecycle / Status Transitions

- [x] The expiry sweep read pending/overdue orders unlocked, then blindly cancelled them via the generic state machine, which also legally allows `confirmed → cancelled` (an admin refund path) — if an admin confirmed (and paid) the order in the gap, the sweep could still cancel it and release its stock, silently destroying a paid reservation — sweep now asserts `expectedFromStatus: 'pending'` and `expiredBefore: now` against the freshly locked row, refusing the transition on any mismatch.
- [x] Same class of race on proof-of-payment: a buyer who uploads their screenshot between the sweep's unlocked read and the locked check must not be auto-cancelled — sweep also refuses to act when `requireNoProof` finds a proof already on file.
- [x] `transitionOrder` held its pool connection through its `finally` while the post-commit email-enqueue step borrowed a second connection from the same pool — enough concurrent transitions reaching the enqueue step at once could exhaust the connection pool (default limit 10), a permanent pool deadlock with no row lock involved — connection is released before enqueueing the transition email.
- [x] Deleting a product variant that still has live (non-cancelled) orders against it would orphan reserved stock accounting — deletion is now refused outright when live orders exist.
- [x] `replaceVariants`'s live-order check ran on an unlocked `SELECT` before the delete transaction opened, so a checkout could commit a brand-new order against a variant in the window between the check and the delete, reproducing the exact "delete a variant with live orders" bug via a race — the check now runs inside the transaction behind `FOR UPDATE` on the locked variant set (ascending id order, matching order creation's lock convention).
- [x] `pickup_code` was generated at order creation and shown immediately on both the order page and the placed-order email — before the seller ever confirmed payment — letting a buyer present an unpaid order's code to event staff; exposure is now gated on `status` being `confirmed`/`completed` (generation unchanged), and the email reads status at send time so a since-confirmed order still gets it correctly.
- [x] A completed COD pickup order (already handed over and paid at the counter) still printed "collect ₫X owed" on the printable roster because paid/collect status was derived from `payment_method` alone — a `completed` order is now always treated as settled regardless of payment method, independent of the caller's status filter (defense in depth, not just the route's `WHERE`).
- [x] Order deadline showed "49h" instead of "48h" right after placing an order — `expires_at` (no fractional-second DB precision) is stored ~1s after the exact N-hour mark, and `Math.ceil` rounding turned that stray second into an extra hour; fixed with a 5-second buffer before rounding, without weakening the "never shows 0 early" guarantee.
- [x] The ~5s expiry sweep means `expires_at` can be in the past while `status` is still `pending` for a real interval — `formatDeadline` explicitly reports `passed:true`/`remainingHours:0` in that window rather than a live countdown, so a buyer is never shown "time remaining" against an order about to be auto-cancelled.
- [x] The manual-confirmation note rendered for COD orders (inviting a bank-transfer screenshot for a payment that's never a transfer) and kept rendering after the deadline passed, contradicting the deadline-passed message shown two lines above — gated behind `showPaymentInstructions && !deadlineInfo?.passed`.
- [x] `formatDeadline` reassembled the buyer-facing deadline by parsing `toLocaleString`'s formatted string (splitting on an assumed literal space/comma) — not guaranteed stable across ICU implementations/browsers, and could silently show a flipped date or the literal string "undefined 09/08" — rewritten to read fields directly from `Intl.DateTimeFormat#formatToParts` by `type`.
- [x] Opaque per-order code — plain sequential `#12` order numbers leaked order volume to anyone comparing two orders; derived a deterministic hash-based `order_code` instead of storing a new field.
- [x] *(uncommitted)* `attachItems`'s `products.images` JSON column can come back from mysql2 as either a string or an already-parsed array — normalized with a `firstImage()` helper that safely handles both shapes, used consistently across order items, the shipping export listing, and the pickup roster.

## Admin Statistics

- [x] A collection created same-day with one sale computed 1÷(1/24)=24 units/day, vaulting a brand-new drop above genuine bestsellers in restock velocity — days-on-sale is floored at 1 day instead of 1 hour.
- [x] The "sorts by velocity descending" test passed only by stable-sort luck (its two fixtures had identical velocity) — rewritten with fixtures whose velocities actually differ, and mutation-verified against reverting the floor.
- [x] `localDayStartUtc()` accepted calendar-invalid dates (e.g. `2026-02-30`) because `new Date()` silently rolls them into a different valid day — the parser now round-trips the constructed date's Y/M/D at UTC+7 and rejects if it doesn't match the input.
- [x] The mysql2 pool had no `timezone` option, so Date query params serialized under the Node process's OS timezone while `orders.created_at` is stamped under MySQL's own session timezone — pool now pins `timezone: "Z"` so date-boundary queries can't silently drift if either side's TZ ever changes.
- [x] `GET /api/admin/stats/drop/abc` (non-numeric id) turned into `Number("abc")` → `NaN` → an unquoted `NaN` token in the SQL WHERE clause → 500 — the raw string param is now passed through so it's safely quoted and 404s instead.
- [x] Unlimited-stock variants showed "—" for sell-through instead of the spec's "không giới hạn" text, contradicting the remaining-stock cell — corrected to match spec.
- [x] Switching quickly between two non-empty collections in the drop-stats view left the previous collection's money on screen under the newly selected title until the fetch resolved, with nothing discarding out-of-order responses — a request-generation ref now drops stale responses, and clearing happens synchronously in `onChange`.
- [x] Pending-COD orders were counted in `order_counts.pending`/`units_sold` but silently dropped from every money bucket (not received, not outstanding, not anywhere) — a fifth `pending_cod` bucket now surfaces that money explicitly in both drop and bookkeeping stats, per-collection too.
- [x] The bookkeeping CSV export read live (unsaved) date-picker input rather than the range that actually produced the on-screen stats — editing the dates after loading, then exporting, silently downloaded a mismatched range/filename; export now reads `date_from`/`date_to` off the loaded `stats` object itself.
- [x] `adminStatsRoutes` bookkeeping test computed "today" via UTC calendar date while the route interprets dates in Asia/Ho_Chi_Minh, causing intermittent failures during the 7 UTC hours (pre-dawn VN time) where the two dates disagree — test now applies the same +7h offset the app uses.

## Email

- [x] `markFailed`'s retry-cap `CASE` re-added `+1` to `attempts`, but MySQL evaluates a single-table UPDATE's SET list left-to-right so `attempts` in the CASE already reflected the just-applied increment — effectively `old_attempts + 2 >= MAX_ATTEMPTS`, permanently failing a row after only 4 real failures instead of the intended 5 — CASE now compares the already-incremented value directly.
- [x] `worker.js`'s tick loop had no in-flight guard, and `claimPending()` was a plain unlocked `SELECT`, so if one tick's work outran the 5s interval, the next tick would resend the same still-pending email rows — a module-level `running` flag now makes an overlapping tick a no-op (also protects the thumbnail loop and expiry sweep under the same guard).
- [x] Queued emails that failed all retries and were marked `failed` were invisible to the admin — surfaced in the admin UI instead of silently sitting failed.
- [x] Pickup-only QR/location content leaked into ship-order transactional emails — the pickup QR block is now skipped for ship-order emails.
- [x] A cancelled order's email still showed the pickup QR and "bring this code at pickup" caption with nothing left to pick up — `isPickup` now also checks the order isn't cancelled.
- [x] Pickup instruction caption/confirmation code shown on the very first (unpaid) `order_placed` email, telling an unpaid buyer to bring a pickup code — gated the caption/code block on `isPaid`, QR image itself stays unconditional (staff still need to look the order up).
- [x] Messenger link in admin settings is sometimes already a full `m.me` URL, sometimes a bare username — unconditional `m.me/` prefixing produced a doubled/broken URL; now detects and only prefixes bare usernames.
- [x] Footer's "automated email" notice rendered twice, once with the email address missing/empty — root cause was stale `email_templates` DB rows saved before a footer refactor, still containing now-removed `{{shop_email}}`/`{{social_links}}` placeholders that silently rendered empty; stale rows deleted so they fall back to current defaults.
- [x] Social-link badges rendered as broken-image icons with overlapping alt text in real mail clients — reverted from data-URI `<img>` SVGs to plain colored-circle+letter badges, then removed entirely after feedback that fake letter badges looked worse than nothing.
- [x] Raw `toLocaleString("vi-VN")` timestamp format on the order status line was inconsistent with the existing deadline line's format — extracted a shared `formatVnDateTime` helper used by both.
- [x] `sender.js` interpolated `${order.pickup_code}` unguarded into every queued pickup email, so a legacy pickup order predating the pickup_code migration (`pickup_code: null`) would email "Mã xác nhận nhận hàng: null" — the email template now guards the block the same way `Order.jsx` already did; the QR image itself still always renders. The printed roster also gained the missing "Mã nhận hàng" column so staff can actually check a spoken code against it.
- [x] Access PIN spliced into the confirmation email lands after the wrong `</div>` (outer wrapper's, not the link card's) — fixed to target the first closing tag after the "Xem đơn hàng" link, verified against a real customized DB template.
- [x] The email send-queue dispatch loop hit one failing send partway through a batch — the loop keeps processing the remaining queued rows instead of aborting the whole batch on a single failure.
- [x] *(uncommitted)* `cancel_reason` was appended at the very end of the cancellation email (after the item list/total), where a buyer's eye doesn't land first — spliced right after the greeting paragraph instead, using a shared `spliceBeforeCardClose` helper (also reused for the PIN block and a new "PIN was in your confirmation email" hint on non-`order_placed` emails).
- [x] *(uncommitted)* Cancelled-order emails previously suppressed the order QR entirely (`showOrderQr = status !== "cancelled"`) — QR is now included even for a cancelled order so the buyer can still check its final state via the link.
- [x] *(uncommitted)* Ship-order emails always said "Phí ship trả cho shipper khi nhận hàng," even for a pickup order that has no shipper — extracted a `shipping_fee_note` template var that's empty for pickup orders.
- [x] *(uncommitted)* `payment_confirmed`'s "what happens next" copy always said "sẽ chuẩn bị và gửi hàng" (will prepare and ship), nonsensical for a pickup order — a `prep_note` var now gives pickup orders their own wording pointing at the pickup code/QR.
- [x] *(uncommitted)* Receiver-info block in emails omitted pickup location/note entirely for pickup orders (only ship address was ever shown) — now adds "Địa điểm nhận"/"Ghi chú nhận hàng" rows for pickup orders, matching what the buyer's order page already shows.
- [x] *(uncommitted)* Order-item rows in emails, the buyer's order page, and admin shipping views showed text only, no photo, making it hard for the buyer/packer to positively identify which product/variant an item is — item queries now LEFT JOIN the variant's own image (falling back to the product's first image) and render a thumbnail everywhere items are listed.
- [x] `payment_note` (an admin-authored custom checkout note, replacing the old per-order transfer code) was echoed a second time in the `order_placed` email body — the pending-payment instructions/QR block on the same page already carried it, so a second copy read strangely out of context — removed from the `order_placed` render specifically (still computed by `buildVars` so a custom admin-edited template can opt back in).

## Security / Auth

- [x] A buyer's order link (order_token) leaks via a casually shared screenshot or forwarded message — public order page, proof upload, and pickup code now require a PIN-derived session token or an admin JWT, not the URL alone.
- [x] A griefer with only a leaked order link overwrites a real buyer's payment-proof photo before admin reviews it — POST proof route now sits behind the same PIN/admin gate instead of only checking order status "pending".
- [x] Buyer-order QR images (`<img src>`) can't carry an Authorization header for the new gated routes — QR/img fetches now go through authenticated axios calls to a `blob:` URL instead of a bare `src`.
- [x] Admin clicks a buyer's order link directly without ever opening `/admin` in that tab — `hasAdminSession()`/`orderAuthHeaders()` now also check `localStorage.admin_token` directly instead of relying on the in-memory axios header only `Admin.jsx`'s login flow sets.
- [x] Admin's 8h access token expires mid support-session now that it also gates the order-page bypass — extended access token lifetime to 1 day, refresh stays 30 days.
- [x] Admin's access token is missing entirely on page load (expired/dropped, or tab reopened past its lifetime) — Admin now attempts the surviving 30-day refresh token on mount instead of forcing straight to the login screen.
- [x] A restored or still-active admin token can still expire mid-session — on a 401/403, the refresh token (30 days) is tried and the triggering request retried before dropping to the login screen.
- [x] A buyer is dropped into the PIN-entry screen immediately after checkout, before ever seeing the confirmation email with the PIN — checkout now seeds a one-time order-access session token into `sessionStorage` so this device/tab skips the gate once.
- [x] CORS/security headers audit: no CORS allowlist, no helmet headers, unpinned JWT algorithm, and payment-proof storage keys built from `Date.now()+Math.random()` (guessable/brute-forceable given sequential order IDs and a public storage proxy) — added a SITE_URL allowlist, helmet with CSP/CORP explicitly disabled (JSON/image-only API), JWT verify pinned to `HS256`, and proof keys switched to `crypto.randomBytes(16)`.
- [x] Rate limiters and login lockout keyed off the leftmost (fully attacker-controlled) entry of `X-Forwarded-For` — set `trust proxy` to exactly the 2 real Nginx hops and switched key functions to Express's `req.ip` via `ipKeyGenerator` (guards against IPv6 /64 rotation too).
- [x] `GET /api/admin/orders(/:id)` did a bare `SELECT *`, leaking `order_token` (a bearer credential for the buyer's own order page) into every admin API response/devtools/HAR capture — stripped in the one serialization chokepoint, leaving internal callers like the email sender unaffected.
- [x] Stripping `order_token` from admin responses silently broke the payment-instructions panel and QR-scanner order lookup (both depended on the token client-side) with no error, only caught by manual testing — replaced with two admin-authenticated server-side lookup endpoints instead of re-exposing the token.
- [x] Admin order search term unbounded — capped to 100 chars since buyer_name/phone/email have no DB index and an unbounded `LIKE` scan added cheap DB load.
- [x] Order-creation DB failures logged the raw error object via `console.error(err)`, and mysql2 embeds the fully-interpolated failing SQL — including the buyer's name/phone/address/email and the order_token — in `err.sql`; logging now emits only `err.message`/`err.code`.
- [x] Every `/api/orders/:token/...` request logged `req.originalUrl` verbatim, writing the buyer's bearer-credential order_token to logs on every page visit — the request logger now redacts the exact 32-lowercase-hex-char token shape only (leaving numeric ids elsewhere in a path untouched).
- [x] Sharp's libvips decodes attacker-supplied bytes on the unauthenticated payment-proof upload route — bumped sharp for a CVE fix rather than deferring, given the reachable attack surface.
- [x] Refreshing the order page after uploading payment proof looked like the upload never happened, since the buyer-facing order response deliberately never exposes the stored proof URL — `has_payment_proof` now lets `ProofUpload` show the success state (text only) even from a fresh page load.
- [x] `PinGate` on the buyer order page displayed the raw Vietnamese lockout message straight from the 429 response body even when the rest of the UI was rendering in English — backend now also returns `retry_after_seconds`, and the frontend builds its own localized `orderPinLocked` string instead of trusting the server's message text verbatim.
- [x] `server.js` fell back to `ADMIN_USERNAME`/`ADMIN_PASSWORD` defaulting to `"admin"`/`"admin"` if either env var was unset — now refuses to boot (`process.exit(1)`) unless both are explicitly set, closing a default-credential path in any environment that forgot to configure them.
- [x] All four upload routes (`/upload/hero`, `/upload/thumbnail`, `/upload/event-image`, `/image`) handed raw request bytes straight to sharp with no upfront format check — `processImage` now validates the buffer's magic bytes via `validateImageBuffer` before decoding, rejecting non-image input with 400 instead of letting sharp's decoder process arbitrary attacker-supplied bytes first.
- [x] `GET /api/admin/payment-settings` returned the raw settings row to the admin's own browser, including fields explicitly marked secret — now runs the response through `publicSettings()` so nothing marked secret ever leaves the server, closing the same class of leak already fixed once for `order_token`.
- [x] Admin's `momo_qr_image` field accepted any string with no scheme check, so a non-`http(s)` value could be stored and later rendered as an `<img src>` — validated to require an `http://`/`https://` prefix before saving.
- [x] `GET /api/wards/:provinceCode` passed the raw path param straight through to the upstream VN-address lookup with no shape check — now requires `/^\d{1,3}$/` and 400s (`invalid_input`) otherwise.

## Admin / Shipping / Roster

- [x] "Đường Hồ Chí Minh" (a real highway through several other provinces) substring-matched as Ho Chi Minh City, wrongly selecting intra-city shipping service for a parcel nowhere near HCMC — province matching now requires a whole-string match (with a follow-up fix repairing an over-tightened first attempt).
- [x] The VTP export writer cleared only the template's example row (row 8), but the bundled template also pre-fills a sequential STT down to row 1045 — a one-order export shipped ~1,037 phantom rows; the writer now clears every column of every row across the whole data region, matching the seller's known-working reference script.
- [x] A COD order with `cod_amount: 0` (a legitimate zero-collection instruction) is distinct from `cod_amount: null` (missing data) — pinned with a regression test so a falsy-check refactor can't collapse the two.
- [x] Tracking-import preview rejected duplicate tracking codes but let duplicate *order* codes through unchecked, so two rows for one order silently applied whichever tracking code landed last (then emailed to the buyer) — duplicate order codes are now rejected file-wide as `duplicate_order_code`.

- [x] Tracking-import's confirm route accepted a row with a blank/missing `tracking_code` and still transitioned the order to "shipped" and queued a "Mã vận đơn: " (blank) email — confirm now validates `order_id`/`tracking_code` per row before calling `transitionOrder`, rejecting invalid rows into the results array without aborting the batch.

- [x] The ViettelPost export route deduped nothing and silently `.filter()`ed out non-integer order ids: a duplicate id produced two xlsx rows (two parcels booked, one buyer) and a non-integer id vanished from the reconciliation count — ids are now walked once, invalid ids routed to `excluded` as `invalid_order_id`, and repeats deduped and reported as `duplicate_order_id`.

- [x] The admin shipping listing hardcoded order codes as `DH${id}` while export/import both used the shared `orderCode()` helper — a future change to `ORDER_CODE_PREFIX` would silently desync what the admin sees from what ships/imports; unified all three call sites onto the one helper.
- [x] ViettelPost export's Column B carried an internal "DH{id}" code meaningless to the seller cross-referencing VTP's own portal — export/import now round-trips the buyer-facing `order_code`, resolved back to an order via a date-range lookup on the code's embedded YYMMDD prefix plus exact-string match (the suffix is a one-way hash).
- [x] `extractPairsFromSheetRows` only checked row 0 for the header, but a real VTP export has 6 rows of company letterhead above the actual header — now scans all rows for the one containing both expected header columns.
- [x] Same function crashed (`Cannot read properties of undefined`) because exceljs's sparse `row.values` has holes that `.map()` skips but `.findIndex()` still visits with `undefined` — fixed by densifying the array with `Array.from` before mapping.
- [x] Tracking-import's file-upload path (`file_base64`) was unimplemented on the confirm/preview route, and exceljs cell values can be rich-text/formula/hyperlink objects rather than plain strings — added a `cellToText` normalizer and enforced `MAX_IMPORT_ROWS` on the upload path too, plus per-request `order_id` dedup so each order appears exactly once in results.
- [x] ShippingExport/ShippingRoster showed the internal "DH{id}" shorthand as the order code, which an admin who only knows an order by its Shopee-style `order_code` couldn't match against AdminOrders or emails — both screens now show the same `formatOrderCode()` value.
- [x] *(uncommitted)* The printable pickup roster had no way to mark an order as packed without switching to the separate shipping-export screen — roster rows now share the same "prepared" toggle/endpoint as shipping export (purely informational, never gates handover), with an expandable per-order item list showing photos.
- [x] Admin's refresh-token silent-refresh only ran as a 401 response interceptor gated on already having an access token — if the access token was missing entirely (expired and dropped), refresh never triggered and the app forced a relogin despite a valid 30-day refresh token — now attempted on mount too.
- [x] *(uncommitted)* Shipping export listing had no way to scope to one collection — `GET /shipping/export/orders` now accepts an optional `collection_id`; omitted, it lists across every collection unchanged from before.

## Shop / Catalog UI

- [x] Vietnamese/diacritic slugify's combining-mark regex used literal invisible Unicode characters that could silently be corrupted by an editor — range escaped to `̀-ͯ` so it stays correct and auditable.

## Deploy / Infra

- [x] The worker Docker container was built but its entrypoint never actually launched `worker.js` — fixed so the deployed worker container runs the intended process instead of sitting idle.
- [x] Two `node worker.js` processes could run at once (a stale process left over from a bad deploy), silently double-processing the same rows with no crash or error — a Redis-backed singleton lease (`SET NX PX`, renewed each tick via a compare-and-extend Lua script) ensures only one process's ticks actually run; TTL set to 6x the ~5s poll tick so ordinary jitter never costs a live worker its own lease while a genuinely dead process's lease clears within ~30s.
- [x] Local dev Redis on the default port collided with an unrelated local project's Redis already bound to that port — added a `REDIS_PORT` override (mirroring the existing `DB_PORT` pattern) and remapped the dev compose port.
- [x] `resetTables()`'s three `FOREIGN_KEY_CHECKS` statements (disable/truncate/re-enable) ran as separate pooled `db.query()` calls, each potentially landing on a different connection for what's a session-scoped setting — pinned all three to one explicitly acquired connection.
- [x] If the `TRUNCATE` in that same reset sequence threw, the re-enable statement was skipped, permanently leaving a pooled connection with FK checks disabled for whatever test reused it next — re-enable now runs in a `finally` so it always fires even on failure.
- [x] SMTP/`SITE_URL`/`SHOP_NAME`/`ADMIN_EMAIL` were read by the app code but never actually wired into either Docker Compose file — order email and QR generation were silently inert in every real deployment; wired through, plus a startup warning when mail is stuck pending because SMTP isn't configured.

- [x] Building/pushing images from an Apple Silicon host with a plain `docker build` stamped the manifest with the build machine's CPU microarchitecture level, which a normal cloud VPS then failed to pull ("no matching manifest") — switched to `docker buildx build --platform linux/amd64` for a truly portable image.
