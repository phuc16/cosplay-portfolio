# Admin UI & Semantic Colour - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the admin panel a semantic colour vocabulary (success / danger / warning / neutral) and use it to fix the two concrete defects the seller reported: order-action buttons that all look identical (including the destructive, irreversible cancel), and a raw-enum orders list and statistics wall that are hard to scan - while the buyer-facing shop keeps its pink brand and gains the same semantic tokens only where it shows state.

**Architecture:** One CSS token addition (`frontend/src/index.css`), one colour-mapping module shared by admin and shop (`frontend/src/constants/statusVariant.js`), one admin-only Vietnamese-label module (`frontend/src/admin/orderLabels.js`, replacing `StatsDrop.jsx`'s local `STATUS_LABELS`), one generic presentational `StatusBadge` component, then targeted edits to `AdminOrders.jsx`, `StatsDrop.jsx`, `Order.jsx`, and `PaymentInstructions.jsx` to consume them. No new dependency, no route, no repo, no backend file.

**Tech Stack:** As the rest of the frontend - React 18, Vite, Tailwind utility classes plus CSS custom properties, Vitest 3 (`react-dom`'s `createRoot`/`act`, this codebase's established component-test pattern - no Testing Library).

**Spec:** `docs/superpowers/specs/2026-08-09-admin-ui-design.md` - read it before touching this plan; every design decision below traces back to it.

## Global Constraints

- **Scope is presentation only.** No API changes, no business logic, no backend file touched. Phase 4's money rules and Phase 5's shipping logic are untouched. A diff reaching a repo, a route, or a backend module means something went wrong.
- Frontend is ESM; tests are Vitest 3 ESM `import`.
- Buyer-facing UI is **bilingual** (`en` + `vi` in `frontend/src/i18n/translations.js`); the **admin panel is hardcoded Vietnamese** - this plan adds no new i18n keys for admin strings. `Order.jsx` (buyer) keeps using `useLanguage()`'s `t()`; `AdminOrders.jsx` / `StatsDrop.jsx` (admin) keep using hardcoded Vietnamese strings, now sourced from `frontend/src/admin/orderLabels.js` instead of being inlined.
- **Never invent a CSS variable.** Every token a component uses must exist in `frontend/src/index.css`, in both `:root` and `.dark`. Task 1 adds a test that greps the file for exactly the token names this plan's later tasks use - no task after Task 1 may reference a `--surface-*`/`--border-*`/`--text-*` token that test doesn't already cover.
- `frontend/src/index.css` structure: raw palette values live in `:root` (e.g. `--gray-500: #6b7280` at line ~29, `--red-500: #ef4444` at line ~38); semantic aliases follow in the same `:root` (e.g. `--text-error: var(--red-500)` at line ~62); dark-mode overrides live in a separate `.dark { ... }` block starting at line 91 (e.g. `--text-error: var(--red-400)` at line ~108). New tokens follow this exact pattern: new raw hues in `:root` (this palette has red and gray/slate ramps but no green or amber - both are needed), aliases in `:root`, overrides in `.dark`.
- The portfolio's pink brand (`--brand`, `--brand-hover`, `--brand-strong`, `--brand-soft`) is untouched and is never used for the new semantic tokens - `--brand` is admin-configurable via site settings (`applyColorScheme`), so it must never carry state meaning.
- Money via `formatVnd` from `frontend/src/utils/money.js` - `formatVnd(n)` returns `` `${Number(n).toLocaleString("vi-VN")}₫` ``, e.g. `formatVnd(35000)` → `"35.000₫"`.
- Mobile: admin usable at 375px; any wide table (`StatsDrop.jsx`'s variant table) already scrolls in its own `overflow-x-auto` container - do not remove that.
- Do not clear state inside a fetch effect; guard refetch paths against out-of-order responses. (No task in this plan adds a new fetch - all changes are to already-fetched data's rendering - but no existing effect's fetch/guard logic in `AdminOrders.jsx`, `StatsDrop.jsx`, or `Order.jsx` may be touched or reordered.)
- Test commands: `cd frontend && npm test && npm run build && npm run lint` (**134 passing** before this plan starts). `npm run lint` has 3 known pre-existing problems in `Portfolio.jsx`/`AdminAlbumImages.jsx` (2 warnings, 1 error) - not this plan's problem; do not fix them here, and do not let a new task introduce a fourth. Backend `cd backend && DB_PORT=3307 DB_PASS=root REDIS_PORT=6380 npm test` (**586 passing**) is run once at the end (Task 7) purely to prove nothing backend changed.
- Commits: Conventional Commits, descriptive bodies, **no `Co-Authored-By` trailer**.

import { describe, it, expect } from "vitest"
import { readFileSync } from "node:fs"
import { fileURLToPath } from "node:url"

const css = readFileSync(fileURLToPath(new URL("../index.css", import.meta.url)), "utf8")

/** Returns the content between the first balanced { ... } pair after `selector`. */
function extractBlock(css, selector) {
  const start = css.indexOf(selector)
  if (start === -1) throw new Error(`selector ${selector} not found in index.css`)
  const braceStart = css.indexOf("{", start)
  let depth = 0
  let i = braceStart
  for (; i < css.length; i++) {
    if (css[i] === "{") depth++
    if (css[i] === "}") { depth--; if (depth === 0) break }
  }
  return css.slice(braceStart + 1, i)
}

const rootBlock = extractBlock(css, ":root")
const darkBlock = extractBlock(css, ".dark {")

const VARIANTS = ["success", "danger", "warning", "neutral"]
const SHADES = ["surface", "border", "text"]

describe("semantic colour tokens (admin UI & shop state)", () => {
  VARIANTS.forEach((variant) => {
    SHADES.forEach((shade) => {
      const name = `--${shade}-${variant}`
      it(`${name} is defined in :root (light mode)`, () => {
        expect(rootBlock).toMatch(new RegExp(`${name}:`))
      })
      it(`${name} is overridden in .dark`, () => {
        expect(darkBlock).toMatch(new RegExp(`${name}:`))
      })
    })
  })

  it("does not define success/warning aliases against --brand, which is admin-configurable", () => {
    const successLine = rootBlock.match(/--text-success:\s*([^;]+);/)?.[1] ?? ""
    const warningLine = rootBlock.match(/--text-warning:\s*([^;]+);/)?.[1] ?? ""
    expect(successLine).not.toMatch(/--brand/)
    expect(warningLine).not.toMatch(/--brand/)
  })
})
```

/**
 * Maps the order status enum (pending/confirmed/shipped/completed/cancelled)
 * and the transition-target enum used for admin action buttons to a
 * semantic colour variant. Colour only, no copy - shared by the
 * hardcoded-Vietnamese admin (frontend/src/admin/orderLabels.js carries the
 * labels) and the bilingual shop (frontend/src/i18n/translations.js carries
 * the labels there).
 *
 * An unknown status/target falls back to "neutral" rather than throwing or
 * returning undefined - a status this module doesn't recognize must still
 * render with *some* semantic-token class, never an invented one.
 */
const STATUS_VARIANT = {
  pending: "warning",
  confirmed: "success",
  shipped: "success",
  completed: "success",
  cancelled: "danger",
}

const ACTION_VARIANT = {
  confirmed: "success",
  shipped: "success",
  completed: "success",
  cancelled: "danger",
}

export function variantForStatus(status) {
  return STATUS_VARIANT[status] || "neutral"
}

export function variantForAction(toStatus) {
  return ACTION_VARIANT[toStatus] || "neutral"
}
```

// Every class string here references only tokens asserted to exist by
// frontend/src/utils/semanticTokens.test.js - do not add a variant or
// token name here without adding it there first.
const VARIANT_CLASSES = {
  success: "bg-[var(--surface-success)] border-[var(--border-success)] text-[var(--text-success)]",
  danger: "bg-[var(--surface-danger)] border-[var(--border-danger)] text-[var(--text-danger)]",
  warning: "bg-[var(--surface-warning)] border-[var(--border-warning)] text-[var(--text-warning)]",
  neutral: "bg-[var(--surface-neutral)] border-[var(--border-neutral)] text-[var(--text-neutral)]",
}

/**
 * A small coloured pill for a status/payment/fulfilment label. Carries no
 * language logic - the caller passes the already-resolved label string
 * (Vietnamese in the admin, translated via t() in the shop) and a variant
 * from frontend/src/constants/statusVariant.js. An unrecognized variant
 * renders with the neutral tokens rather than an invented or empty class.
 */
export default function StatusBadge({ label, variant = "neutral" }) {
  const cls = VARIANT_CLASSES[variant] || VARIANT_CLASSES.neutral
  return (
    <span className={`inline-block px-2 py-0.5 text-xs rounded-full border font-medium whitespace-nowrap ${cls}`}>
      {label}
    </span>
  )
}
